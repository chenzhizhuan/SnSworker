# 招标文件分析技能

Use this skill to decompose tender documents, extract scoring criteria and hard requirements, build a response matrix, and design a bid proposal framework that downstream writers and reviewers can act on.

## Core Principle

你是投标链条的第一环——"读懂再写"。你的输出质量直接决定标书编写师能不能写出高分内容、合规审查员能不能精准审查。

Do not draft any proposal content. Your job ends at the response matrix and proposal framework. Everything after that belongs to the bid-writer and compliance-reviewer.

Treat analysis outputs as structured decision support, not as final conclusions. Mark uncertain items as `需人工确认`, never infer or fabricate.

## Workflow

### Step 1: 招标文件深度拆解

**做什么：** 决定投标后，对招标文件做逐条深度拆解，提取所有硬性要求、否决条款、评分标准和隐性风险。

**输入：**
- 完整招标文件（PDF/Word）

**输出：**

**1.1 资格条件清单**

| 序号 | 资格要求 | 原文摘录 | 我司是否满足 | 证明材料 | 需人工确认 |
|------|---------|---------|-------------|---------|-----------|
| 1 | | | 满足/不满足/待确认 | | |

**1.2 否决条款清单**

| 序号 | 否决条件 | 原文摘录 | 风险等级 | 我司当前状态 | 需准备材料 | 需人工确认 |
|------|---------|---------|---------|-------------|-----------|-----------|
| 1 | | | 高/中/低 | | | |

否决条款是废标的直接触发条件，必须逐条提取，不得遗漏。重点关注：
- 资质不满足即废标的条款
- 签章、密封、格式要求
- 投标有效期、保证金要求
- 特定业绩/人员/证书的硬性门槛

**1.3 评分标准矩阵**

| 评分类别 | 评分项 | 分值 | 评分细则摘要 | 响应难度 | 建议响应策略 | 需补充材料 |
|---------|-------|------|------------|---------|------------|-----------|
| 技术 | | | | 高/中/低 | | |
| 商务 | | | | | | |
| 报价 | | | | | | |
| 服务 | | | | | | |
| 合规/格式 | | | | | | |

评分矩阵要做到：
- 不得遗漏任何评分项
- 区分"客观分"（有明确量化标准）和"主观分"（评委自由裁量）
- 对高分值项标注"重点投入"
- 对难度高的项提前标注"需补充材料"

**1.4 关键时间节点表**

| 节点 | 时间 | 要求 | 备注 |
|------|------|------|------|
| 答疑截止 | | | |
| 标书递交截止 | | | |
| 开标时间 | | | |
| 保证金到账截止 | | | |

**1.5 特殊要求与隐性风险**

| 要求/风险 | 原文依据 | 影响范围 | 应对建议 |
|----------|---------|---------|---------|

隐性风险包括但不限于：
- 评分标准中模糊表述（如"优/良/中/差"无量化标准）
- 隐含的本地化偏好
- 特定品牌/技术路线的倾向性描述
- 对联合体或分包的限制

**约束：**
- 只基于已提供的招标文件提取，不得编造未出现的要求
- 否决条款必须原文摘录，不得概括或改写后丢失关键信息
- 评分标准如有模糊之处，标注 `需人工确认`，不得自行解读
- 隐性风险只是提醒，不代替人做判断

### Step 2: 构建响应矩阵

**做什么：** 把前面提取的硬性要求、否决条款和评分标准，映射到投标文件的具体章节，形成标书编写师可以直接使用的工作清单。

**输入：**
- Step 1 输出的全部拆解结果
- 投标文件目录/框架（如有）
- 分工信息（我负责哪些章节）

**输出：**

| 招标要求/评分点 | 类别 | 分值 | 责任归属 | 响应章节 | 响应要点 | 需要材料 | 当前状态 | 风险提示 |
|---------------|------|------|---------|---------|---------|---------|---------|---------|
| | 技术/商务/报价/合规 | | 我负责/他人负责/仅作参考 | | | | 已具备/待补充/需确认/范围外 | |

响应矩阵是整个投标工作的"总账"：
- 每个评分项必须有明确的响应章节归属
- `待补充` 项必须说明需要什么材料
- `需确认` 项必须说明需要谁确认什么
- `范围外` 项只做关联提醒，不展开

**约束：**
- 响应矩阵必须覆盖所有评分项，不得遗漏
- 不要把范围外内容混入我负责的章节
- 高风险项（否决条款相关）单独标注
- 响应矩阵完成后，输出工作摘要：已具备 X 项、待补充 X 项、需确认 X 项、范围外 X 项

**责任归属确认（必须人工确认）：**
- 响应矩阵中的"责任归属"列默认填写"待确认"，除非用户已明确告知分工
- 完成后必须提示用户确认：哪些章节由我司编写、哪些由其他单位提供、哪些仅作参考
- 不要自行推断责任归属，必须由人工明确指定

---

### Step 3: 输出投标文件框架

**做什么：** 基于招标文件中关于"投标文件格式"要求的章节和评分标准，输出一份完整的投标文件框架文档。这份框架是标书编写师的工作蓝图——拿到后能直接知道每一章写什么、怎么写、有什么约束。

**输入：**
- Step 2 输出的响应矩阵
- 评分标准矩阵
- 招标文件中关于投标文件格式要求的章节（**核心依据**——决定了框架的章节结构、顺序、编号。该章节可能位于第六章或其他章节，需根据目录定位，通常标题含"投标文件格式""投标文件组成""投标文件编制"等关键词）
- 招标文件中"投标人须知"的投标文件编制要求（如有）
- 历史投标文件框架（如有，可作为风格参考）

**输出：**

#### 3.1 提取投标文件结构

**做什么：** 从招标文件中关于投标文件格式要求的章节提取投标文件的完整目录结构。

该章节通常会列出所有分册和章节的编号、标题、顺序。这是投标文件的"法定骨架"，必须严格遵循。

提取结果输出为：

| 分册 | 章节编号 | 章节标题 | 是否★ | 是否"如有" | 对应评分项 | 分值 |
|------|---------|---------|-------|-----------|-----------|------|
| 第一分册 商务投标文件 | 1 | 商务投标文件封面 | — | — | — | — |
| 第一分册 商务投标文件 | 2 | 初步评审索引表 | — | — | 初步评审 | — |
| 第一分册 商务投标文件 | 3 | 商务评审索引表 | — | — | 商务评审 | — |
| 第一分册 商务投标文件 | 5 | ★投标函 | ★ | — | — | — |
| ... | ... | ... | ... | ... | ... | ... |
| 第二分册 技术投标文件 | 37 | 技术方案 | — | — | 技术方案 | 5 |
| ... | ... | ... | ... | ... | ... | ... |
| 第三分册 报价文件 | 49 | 投标一览表 | — | — | 投标报价 | 50 |

**标注规则：**
- ★标记：章节标题中带★的，标注为★（实质性条款，不提供则废标）
- "如有"标记：章节标题中带"如有"的，标注为条件性章节（满足条件时提供）
- 对应评分项：从评分矩阵中找到该章节对应的评分项，无评分的填 `—`

**约束：**
- 章节顺序、编号、标题必须与招标文件中格式要求章节完全一致，不得自行调整
- 如果招标文件没有明确的投标文件格式要求章节，按行业惯例（商务/技术/报价三册）输出建议结构，并标注"建议结构，非招标文件强制要求"

#### 3.2 逐章展开框架内容

**做什么：** 对每个章节展开详细内容说明，形成可直接使用的编写蓝图。

**输出格式要求（重要）：**

框架最终输出为一份**清洁的骨架文档**（Markdown 或 docx），供标书编写师直接使用。格式要求：

1. **目录（强制生成项，不得省略）**：框架文档开头（封面之后、正文之前）**必须生成完整目录结构**，列出所有分册、章节编号及标题，便于快速定位。目录为强制生成项——生成 .docx 时必须把目录实际渲染进文档正文（不得仅在说明文字中提及目录）。目录层级：`# 目录` → 分册名 → 章节编号+标题（逐条列出全部章节，含★标记）；分析报告等其他交付文档同样必须在开头生成完整目录
2. **章节标题带编号，分册带序号**：使用 `# 第X分册 分册名` → `## 编号 章节标题` → `### 编号.X 子章节` 的层级结构
   - 三个分册的一级标题必须标注分册序号：`# 第一分册 商务投标文件`、`# 第二分册 技术投标文件`、`# 第三分册 报价文件`
   - 示例：`# 第一分册 商务投标文件` → `## 1 商务投标文件封面` → `## 5 ★投标函` → `### 13.1 资格审查资料-基本条件`
3. **模板文字用块引用**：招标文件提供的模板正文用 `>` 块引用包裹
4. **分页符**：每个章节之间用 `**\**` 分隔
5. **不添加分析元数据**：框架文档中不要出现"类型：格式性内容""对应评分项：XXX""建议篇幅：X页"等分析注释。这些信息属于 Step 1-2 的分析产出，不应混入框架文档

对每个章节，在框架文档中提供以下信息（简洁格式）：

```
## X [章节标题]

> [招标文件提供的模板正文，如有]

**内容要点：**
- [该章节需要填写/编写的核心内容，2-5个要点]

**需要材料：**
- [列出编写该章节所需的具体材料]

**★实质性条款 / 否决风险：**（如适用）
- [废标风险提醒，非★章节可省略此项]
```

**章节类型判断规则：**
- **格式性内容**：投标函、授权书、承诺函等——有固定模板，按模板填写即可
- **资格性内容**：营业执照、业绩证明、社保记录等——提供证明材料扫描件
- **评分响应内容**：技术方案、安全管理、培训方案等——需要根据评分标准编写
- **报价内容**：投标一览表、报价明细等——需要商务核算后填写

**对"评分响应内容"类章节的额外要求：**
- 必须映射到评分矩阵中的具体评分项
- 必须摘录该评分项的评分细则（从评分标准矩阵中复制）
- 必须给出建议篇幅（根据分值和评分细则的详细程度）
- 必须标注主观分/客观分（主观分需要差异化内容，客观分需要精确响应）

**"编号子项清单"标题化规则（通用，适用于所有招标文件）：**
- 招标文件章节内凡以"1. 2. 3. …"编号列出的子项清单（如技术建议书下的"1. 企业整体实力：提供有效的认证证书扫描件""2. 整体服务方案：提供方案，格式自拟"等），在投标文件框架中必须逐条转为下一级标题（Heading 3，标题格式"父章节号.X 子项名"），不得作为正文段落平铺。
- 标题只保留子项名称（去掉编号、"："及其后的材料/格式要求）；招标文件原文的材料/格式要求放入标题下方的块引用（`>`）中，格式为"> 招标文件要求：XXX"。
- 每个子项标题下仍按通用格式给出**内容要点**与**需要材料**。
- 具体子项名称与要求以各招标文件原文为准，不得套用其他项目的子项内容；此规则只约束"编号子项清单"的标题化处理方式，不限定子项内容本身。

#### 3.3 评审索引表编制指引

**做什么：** 为初步评审索引表、商务评审索引表、技术服务评审索引表提供编制指引。

评审索引表是评标委员会快速定位投标文件内容的导航表，必须与评分标准严格对应。

输出格式：

| 索引表类型 | 对应评审阶段 | 编制依据 | 填写要点 |
|-----------|------------|---------|---------|
| 初步评审索引表 | 初步评审（形式+资格+响应性） | 第三章评标办法2.1条 | 按评审标准顺序逐条罗列，标注投标文件中的对应位置和页码 |
| 商务评审索引表 | 详细评审-商务部分 | 第三章评标办法2.2条商务评分项 | 按商务评分项顺序罗列，标注对应章节和页码 |
| 技术服务评审索引表 | 详细评审-技术+服务部分 | 第三章评标办法2.2条技术/服务评分项 | 按技术+服务评分项顺序罗列，标注对应章节和页码 |

**约束：**
- 索引表的评审因素顺序必须与第三章评标办法的评审标准顺序一致
- 索引表的"对应页码"列在框架阶段留空（待正文完成后填写）
- 索引表的"投标文件组成"列需说明该评审因素对应的具体文件内容

#### 3.4 篇幅分配与编写规划

**3.4.1 篇幅分配建议**

| 分册 | 总页数建议 | 评分响应页数 | 格式性内容页数 | 分配依据 |
|------|----------|------------|-------------|---------|
| 第一分册 商务投标文件 | | | | 格式性内容精简为主；企业能力/业绩等评分项按分值分配 |
| 第二分册 技术投标文件 | | | | 按各评分项分值权重分配，高分值项多分配 |
| 第三分册 报价文件 | | | | 按招标文件格式要求 |
| 合计 | | | | |

篇幅分配原则：
- 价格分占比最高的（通常50分），报价文件精简准确即可，不需要大量篇幅
- 技术分占比最高的部分应获得最多篇幅，且各章节篇幅与分值成正比
- 主观评分项（如技术方案5分，评分细则分4档）需要充分篇幅展示差异化内容
- 客观评分项（如人员配备6分，有证书就得3分）精简响应+证明材料即可
- 格式性内容（投标函、授权书等）不膨胀，按模板填写即可
- 如果招标文件有总页数或文件编制情况评分（如本项目2分），在框架阶段就做好总量控制

**3.4.2 编写顺序建议**

根据章节间的依赖关系和重要程度，建议编写顺序：
1. **第一批**：高分值、高难度的技术/服务方案章节（技术方案、安全管理、服务管理等）
2. **第二批**：有明确模板的商务格式章节（投标函、授权书、承诺函等）
3. **第三批**：需要收集证明材料的资格/业绩章节（资质证书、业绩合同、社保记录等）
4. **第四批**：报价文件（依赖技术方案和人员配备确定后才能定价）
5. **最后**：评审索引表（所有章节完成后才能填写页码）

**3.4.3 责任归属建议**

| 角色 | 典型负责章节 | 说明 |
|------|------------|------|
| 标书编写师（技术） | 技术方案、安全管理、测试验收培训、服务管理、培训方案、进度计划 | 核心评分响应内容 |
| 标书编写师（商务） | 商务格式章节、资格资料、业绩、企业能力 | 格式性+资格性内容 |
| 商务人员 | 报价文件、投标一览表 | 需要成本核算和商务决策 |
| 行政/法务 | 投标函、授权书、承诺函、签章 | 需要法人授权和公章 |
| 项目经理 | 人员配备、常驻服务团队 | 需要确认人员安排和证书 |

**约束：**
- 如果招标文件规定了投标文件的固定结构，必须严格遵循，不得自行调整章节顺序或合并拆分
- 框架只到章节级别，不展开到正文内容（正文是编写师的工作）
- 每个评分响应章节必须映射到评分点，格式性/资格性章节标注类型即可
- 建议篇幅是参考值，不是硬性要求，编写师可根据实际情况调整
- 不得编造招标文件中未要求的章节或内容
- 框架完成后，提示用户确认：章节结构是否合理、责任归属是否正确、是否有遗漏

### Step 4: 交付与衔接

**做什么：** 汇总分析成果，明确移交给标书编写师和合规审查员的内容。

**输出：**

**必须输出为两个独立文件：**

| 文件 | 内容 | 用途 |
|------|------|------|
| 招标文件分析报告 | Step 1-2 的全部分析成果（资格条件清单、否决条款清单、评分标准矩阵、响应矩阵、关键时间节点、隐性风险、分析成果摘要）。**文档开头必须包含完整目录**（列出全部章节编号及标题） | 供人工审阅和决策 |
| 投标文件框架 | Step 3 输出的清洁骨架文档（Markdown 或 docx），不含任何分析元数据。**文档开头必须包含完整目录**（列出全部 3 个分册及其全部章节编号、标题） | 供标书编写师直接使用 |

**两个文件必须分开输出，不得合并为一个文件。**

移交给标书编写师：
- 响应矩阵（作为编写依据）
- 评分标准矩阵（作为篇幅分配依据）
- 投标文件框架（作为大纲设计和章节编写的蓝图）
- 否决条款清单（编写时必须规避）
- 需要补充的材料清单

移交给合规审查员：
- 否决条款清单（审查时逐条核对）
- 资格条件清单（审查时逐条验证）
- 评分标准矩阵（审查时检查响应覆盖率）

**约束：**
- 分析成果和正文内容严格分离，你不写正文

- 每一步结束后都提示：这一步做了什么、得到什么结果、下一步需要用户提供或确认什么
- 本技能全部完成后，必须提示用户：`招标文件分析技能已完成，下一步建议使用「标书编写技能」，基于响应矩阵、评分标准矩阵和投标文件框架继续编写标书正文。`

## Document Formatting Specifications

设计投标文件框架和生成 `.docx` 文件时，遵循以下排版规范：

### 正文段落
- 字体：中文宋体 (SimSun) + 西文 Times New Roman，小四 (12pt = 24 half-points)
- 行距：1.5 倍行距 (w:line="360" w:lineRule="auto")
- 首行缩进：2 字符 (w:firstLineChars="200")
- 保留已有加粗格式

### 各级标题
所有标题统一：1.5 倍行距、加粗、颜色 auto。

- **一级标题**：黑体 (SimHei)，小三 (15pt = 30 half-points)
- **二级标题**：中文黑体 + 西文 Times New Roman，四号 (14pt = 28 half-points)
- **三级标题**：中文黑体 + 西文 Times New Roman，四号 (14pt = 28 half-points)
- **四级~七级标题**：中文黑体 + 西文 Times New Roman，小四 (12pt = 24 half-points)

### 表格内文字
- 字体：中文宋体 + 西文 Times New Roman，五号 (10.5pt = 21 half-points)

### 表格标题
- 位置：表格上方独立段落
- 对齐：居中
- 字体：宋体 (SimSun)，小四 (12pt)，斜体
- 无编号前缀（如"核心业务系统建设范围"，而非"表39-5-1 核心业务系统建设范围"）
- 表格标题段落不缩进

### 技术实现说明
- **生成 .docx 必须用 python-docx 直接写 OOXML（execute_code / runSkillScript），禁止用 renderDocx / renderDocxFromFile 等通用 Markdown 渲染器交付最终文档**——通用渲染器不产出 Word 内置 Heading 样式、不生成大纲级别、不渲染目录页，交付出去就是"无目录、标题全是正文样式"的残缺文档
- 标题必须使用 Word 内置样式：`doc.add_paragraph(style=f"Heading {level}")`，一级 Heading 1（黑体小三15pt）、二级 Heading 2（黑体四号14pt）、三级 Heading 3（黑体四号14pt），并显式写入 `w:outlineLvl`（`outline.set(qn("w:val"), str(level-1))`）确保 Word 导航窗格/大纲视图可识别为标题
- 目录页用普通段落逐条真实渲染进文档正文（封面之后、正文之前，独立成页）：`# 目录` → 分册名 → 章节编号+标题（含★标记），按层级缩进
- 中文西文混排：用 `w:rFonts` 分别设置 `w:eastAsia`（宋体/黑体）与 `w:ascii`/`w:hAnsi`（Times New Roman）
- 1.5 倍行距用 `w:spacing` 的 `w:line="360" w:lineRule="auto"`；首行缩进 2 字符用 `w:ind` 的 `w:firstLineChars="200"`
- 使用 python-docx 操作 OOXML，不要用正则替换（避免 XML 损坏）
- 章节定位：用文本内容匹配（如"成功案例"→"服务管理方案"），不要用样式名
- 表格标题插入：先扫描所有表格获取 body index，再倒序插入避免索引偏移
- 用 body-index 集合跳过已用作表格标题的段落，避免重复格式化

### 首稿达标闸门（First-Draft Quality Gate，强制）
**禁止"先生成残缺版、等用户反馈后再补目录/格式"。** 每个 .docx 交付物必须在**第一次生成**时就完整达标，生成脚本内必须包含回读自检，全部通过才算完成：

1. **回读验证标题样式**：用 `Document(OUT)` 重新打开，断言 Heading 1 / Heading 2 / Heading 3 段落数符合预期（如 33 章 → 33 个 Heading 2；分册 → Heading 1），任一不符即修正后重新生成
2. **验证章节齐全且顺序正确**：遍历 Heading 2 标题文本，确认章节编号 1..N 逐个存在且出现位置单调递增；缺失或乱序即修正
3. **验证目录页已渲染**：文档段落文本中能找到"目录"标题，且其后紧跟分册名与章节条目；目录条目数 = 实际章节数
4. **验证大纲级别**：抽查标题段落 `pPr` 下存在 `w:outlineLvl`（Word 导航窗格可识别）
5. **验证排版规范**：抽查正文段落的 `w:spacing` line=360、`w:ind` firstLineChars=200、标题字体为黑体
6. 自检脚本将检查结果打印到 stdout（标题数量/缺失列表/顺序 OK/目录位置），**确认全部通过后才向用户交付下载链接**

## Output Format Rules

**强制总则（所有交付文档必须遵守，且首稿即须达标）：**
- **首稿即达标**：第一次生成的 .docx 就必须包含完整目录和正确排版（见"首稿达标闸门"），禁止先交付残缺版等用户反馈再返工；生成脚本内必须内置回读自检，全部通过后才交付下载链接
- 所有交付文档（招标文件分析报告、投标文件框架）**开头必须包含完整目录**：封面/标题之后、正文之前，将全部章节编号及标题实际渲染进文档正文（目录为强制生成项，不得仅在说明文字中提及；docx 渲染时必须真正输出目录页）
- 所有交付文档的排版格式必须遵循 Document Formatting Specifications：标题黑体（一级小三15pt、二级/三级四号14pt）、正文宋体+Times New Roman 小四12pt、1.5倍行距、首行缩进2字符、表格文字宋体五号10.5pt、表格标题居中斜体无编号
- 交付 .docx 用 python-docx 直接生成并回读验证（禁止用通用 Markdown 渲染器交付最终文档，见"技术实现说明"）

- 所有分析结果用表格输出，便于下游直接使用
- 表格字段不得省略，缺失信息填 `—` 或 `待补充`
- 风险等级统一使用：`高`（可能废标或重大扣分）、`中`（可能影响评分或完整性）、`低`（需注意但可控）
- 状态统一使用：`已具备`、`待补充`、`需确认`、`范围外`
- 责任归属统一使用：`我负责`、`他人负责`、`仅作参考`、`暂不处理`

## Risk Rules

- 不得编造公司不具备的资质、业绩、人员或证书
- 不得对模糊条款做确定性解读，必须标注 `需人工确认`
- 否决条款必须原文摘录，不得概括改写
- 分析输出和正文内容严格分离
- 如发现致命风险（如核心资质不满足），立即标注并建议人工确认，不要继续推进后续步骤
