# Bid Proposal Writing Style

Use this reference before drafting proposal prose, revising proposal sections, or creating a section outline from tender requirements.

## Preferred Input Order

When available, use source materials in this order:

1. User-approved prior draft or strong sample, such as a previous reviewed proposal section.
2. Tender document and scoring criteria.
3. User-provided company materials, templates, delivery records, product descriptions, or technical notes.
4. Conservative industry-standard wording only when the tender and materials do not provide enough detail.

Do not let generic proposal patterns override a strong user-provided sample.

## Tender Grounding

- Read the tender closely and extract usable substance before writing.
- Use the tender's requirements, service scope, deliverables, evaluation points, and terminology as factual grounding.
- Write the final prose as the bidder's response. Do not expose the source-reading process.
- Do not write `根据招标文件`, `依据招标文件要求`, `详见招标文件`, `招标文件第 X 条`, or similar source-index phrasing.
- Do not invent facts when the tender or provided materials are silent. Use `待补充素材` or `需人工确认` in analysis outputs; in final prose, prefer cautious wording or ask for confirmation.

## Bidder Perspective

- Use `我司` as the default subject.
- Write from the bidder's perspective: responsible, practical, cooperative, and sincere.
- Show commitment through actions: plans, mechanisms, checkpoints, deliverables, escalation paths, and review methods.
- Avoid empty enthusiasm. Phrases such as `高度重视`, `加强管理`, `确保质量`, and `全力保障` must be followed by concrete measures if used.

## Heading Style

- Prefer concise, natural headings.
- Avoid over-fragmented headings.
- Avoid long paired headings such as `XXX与XXX`, `XXX和XXX`, `XXX及XXX`.
- Avoid generic AI-like headings that sound abstract but do not carry content.
- Keep only headings that can support substantial, useful text.
- If a heading would only contain 1-2 short paragraphs, merge it into a broader heading.
- When editing a Word document with automatic numbering, do not include manual section numbers in heading text.

## Paragraph Density

- Each heading should contain enough developed prose to feel like a real proposal section.
- Avoid short, thin sections made of 1-2 brief paragraphs.
- Prefer fewer headings with richer paragraphs over many headings with shallow content.
- Expand through explanation of:
  - project understanding,
  - implementation logic,
  - stage arrangement,
  - resource coordination,
  - risk handling,
  - deliverable formation,
  - review and closure,
  - cross-section coordination.

## Page Count Handling

If the user asks for a page count:

- Clarify whether the page count applies to the whole document or a single section.
- Verify page count from the actual rendered or Word-computed document, not by guessing from word count.
- Do not use repeated tables, duplicated templates, or fragmented headings just to increase pages.
- Increase length through useful content: scenario-based explanations, execution details, tender-specific response depth, quality control, risk control, and delivery logic.
- If automatic Word numbering is used, never manually prepend numbers such as `23.8.1` to heading text.
- After page-count expansion, run a duplicate-content review. Page count must not be achieved through copied paragraphs, repeated tables, or repeated scenario blocks.

## Visual Aid Use

Use visuals only when they make the proposal easier to understand. Do not add images only for decoration, page count, or a polished-looking surface.

Good visual candidates:

- Implementation process flow.
- Service response loop.
- Project schedule or stage roadmap.
- Responsibility and collaboration flow.
- Problem handling and escalation path.
- Risk warning and correction mechanism.
- Deliverable formation and review closure path.

When generating visuals:

- Use image2 when AI-generated images are needed.
- Keep visuals businesslike, clean, and easy to read.
- Use Chinese labels consistent with the proposal prose.
- Do not introduce facts, tools, product names, personnel, dates, or commitments not supported by the tender or provided materials.
- Place the visual near the prose it explains.
- Add a short caption or lead-in paragraph explaining why the visual exists.
- If a simple table or prose explanation is clearer than a graphic, do not generate an image.

## Anti-AI Style Checks

Before delivery, check for:

- Too many headings.
- Headings that repeat the same phrase with small variations.
- Manual numbers inside heading text when Word automatic numbering is active.
- Adjacent tables with similar fields.
- Generic project-management language not tied to tender scope.
- Thin paragraphs under headings.
- Repeated wording such as `闭环管理`, `动态调整`, `持续优化` without concrete context.
- Source-index wording that reveals tender citation behavior.
- Decorative visuals that do not clarify actual proposal content.

If any issue appears, revise structurally rather than only polishing wording.

## Duplicate Content Checks

Before final delivery, proactively check:

- Exact duplicate paragraphs.
- Repeated blocks with only one or two words changed.
- Repeated tables with the same columns and similar rows.
- Repeated headings with different numbers but the same meaning.
- Reused scenario descriptions that do not add new tender-specific value.

If exact duplicate content exists, remove or consolidate it before delivery. If near-duplicate content exists, rewrite it with a distinct purpose or merge it into a broader section.

## Heading Numbering Checks

When editing `.docx` files:

- Detect whether headings already use Word automatic numbering.
- If automatic numbering is active, heading text must contain only the title words, not `23.8.1`-style manual numbers.
- Check rendered or extracted headings for duplicated numbering patterns such as `23.8.15.4 23.8.15.4`.
- Fix duplicate numbering proactively, without waiting for the user to notice it.
