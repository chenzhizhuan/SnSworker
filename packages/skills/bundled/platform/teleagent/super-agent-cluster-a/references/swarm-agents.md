## 共享专家（始终在线）

借鉴K3的共享专家设计，CARS设置3个共享专家不参与路由选择，始终在线处理通用能力。架构设计依据详见 [k3-enhancement-modules.md](k3-enhancement-modules.md) 架构总纲。

### Sentinel（安全审查，每次任务100%强制在线）

**核心职责**：代码执行前安全审查、输入/输出安全过滤、代码执行门禁

**强制执行**：每次任务中任何涉及代码执行、外部API调用、文件写入的操作均必须经Sentinel审查，不可跳过。即使L1轻量任务也不得跳过安全审查。

安全审查清单（Executor运行代码前必检）：

- [ ] 代码不包含外传敏感数据的操作（上传密码、密钥、隐私信息到外部）
- [ ] 代码不执行系统级破坏操作（删除系统文件、修改注册表、关闭防火墙）
- [ ] 文件操作限于工作目录和.temp目录
- [ ] API调用目标URL经过安全校验（非内网地址、非可疑域名）
- [ ] 代码执行时间不超过30秒

### ContextManager（上下文管理，每次任务100%强制在线）

**核心职责**：双轨上下文压缩L0-L3、信息密度评分、KV Cache共享

**强制执行**：每次任务的上下文变化必须由ContextManager追踪和压缩，不可手动省略。

分层语义压缩（L0原文→L1摘要→L2关键词→L3向量索引）及信息保真度评分机制详见 [k3-enhancement-modules.md](k3-enhancement-modules.md) 模块3。

### Decomposer（目标分解，每次任务100%强制在线）

**核心职责**：目标解析、子任务拆分、动态Agent生成

**强制执行**：每次任务必须经Decomposer完整执行目标解析+任务分解，不可跳过直接进入Swarm。

目标解析流程：
1. 显性目标提取——从用户输入中直接提取明确要求
2. 隐性目标推断——推断用户未明说但对结果至关重要的需求
3. 目标置信度评估——对推断结果打分，低于0.8时向用户确认而非猜测执行

## 动态Agent生成机制

CARS中Agent不是预定义角色，而是根据子任务特征自动生成能力配置。主Agent自主决定每个子任务需要什么能力的Agent。**LangGraph状态机编排**：Agent生成→执行→消亡的全生命周期以LangGraph StateGraph管理，支持checkpoint恢复和中断续接。**Programmatic Tool Calling（PTC）**（借鉴Anthropic 2026年）：[Agent-编码型]通过代码编排工具调用替代逐个API调用，降低token消耗+提升执行可靠性。**MCP无状态化设计**（2026.7）：每次工具调用携带完整上下文快照，避免会话中断丢失状态。

### Agent生成流程

每个Agent内部运行TAOR（Think-Act-Observe-Reflect）循环作为核心推理引擎，替代线性推理链。TAOR完整定义（四阶循环+双反馈闭环+层级深度）详见 [k3-enhancement-modules.md §TAOR思考循环](k3-enhancement-modules.md)，此处不重复。

```text
[子任务输入] → 分析子任务特征（领域/复杂度/模态/输出类型）
  → 匹配Agent能力模板（搜索型/分析型/编码型/核查型/验证型/综合型/运维型/元认知）
  → 注入领域知识要点（从MemoryKeeper获取相关记忆基线）
  → 配置工具集（按需配置Python/统计库/搜索工具/API等）
  → 设置验证策略（内置自验阈值和方法）
  → spawn Agent实例 → 执行子任务 → 完成后消亡
```

### [Agent-编码型]深度能力（借鉴 Matt Pocock code-review + diagnosing-bugs，⛔每次代码任务100%强制）

**双轴代码审查（借鉴 code-review 技能）**：每次代码审查必须沿两个独立轴并行执行，不可只查一轴：
1. **标准轴（Standards）**：代码是否符合项目编码规范/代码风格/架构约定（命名、格式、模块化、错误处理、文档）
2. **规格轴（Spec）**：代码是否实现任务要求的功能（需求覆盖、边界条件、验收标准、与原始规格逐项对照）

两轴分别产出独立审查报告，最终合并呈现。禁止只查规范不查功能，或只查功能不查规范。

**Bug诊断循环（借鉴 diagnosing-bugs）**：当代码报告 Bug/异常/性能回退时，执行纪律化诊断循环：
1. **红绿灯**：先复现（红灯=可复现/绿灯=不可复现），不可复现先收集更多现场信息
2. **最小化**：将问题缩小到最小复现单元（MRE），删除无关代码路径
3. **假设生成**：基于根因假设（依赖/状态/时序/环境/数据）生成2-3个候选解释
4. **插桩验证**：通过日志/断点/测试断言验证假设，排除错误假设
5. **修复**：最小变更修复（避免引入新行为），补回归测试
6. **回归验证**：修复后验证原场景+边缘场景+既有功能无回退
⛔禁止在未复现/未最小化时直接猜测修复；禁止无回归测试的裸修复。

**代码审查 5 项强制检查清单**：安全性（注入/SQL/敏感信息泄漏/越权）、正确性（边界条件/并发/异常路径）、可维护性（模块化/可读性/命名）、性能（复杂度/资源泄漏）、可测试性（可测性/断言/用例覆盖）。任一未检查→审查不完整，退回补查。

**代码任务产出**：所有代码变更必须输出「变更摘要+审查记录+回归结果」三段式结论，禁止只给代码不给结论。

**TDD红绿开发循环（借鉴 tdd 技能）**：功能开发任务强制测试先行，禁止裸实现：
1. 🔴 **红（Red）**：先写失败测试用例，验证确实失败（若直接通过→测试无效退回）
2. 🟢 **绿（Green）**：最小实现让测试通过，不做额外设计
3. 🔧 **重构（Refactor）**：消除重复改善结构，保持测试全绿
- 一次一个垂直切片，禁止大爆炸式一次性写全部代码
- 每阶段嵌入Step标注（[TDD-红]/[TDD-绿]/[TDD-重构]），禁止只标最终结果
- 无法编写测试的代码（纯脚本探针）须标注"⛔无测试覆盖原因"，核心逻辑尽量抽为可测试函数
- 与Bug诊断循环互补：诊断循环修已存在Bug，TDD循环建新功能

**代码格式与步骤检查（V11新增，⛔每次代码任务100%强制）**：编码型在提交代码变更前，必须执行以下格式与步骤检查：
1. **步骤完整性检查**：确认代码变更遵循了任务分解中分配给编码型的全部步骤——任务分解的每个子步骤是否有对应代码实现？是否有步骤被遗漏？⛔禁止跳过任务分解中分配的步骤直接写实现。检查结果以Step标注输出："步骤完整性：✅ N/N步已实现"或"步骤完整性：⚠️ 缺失第X步，退回补全"
2. **强制规则遵守检查**：确认代码遵守SKILL.md中所有适用于编码型的强制规则——包括双轴审查、5项检查清单、Bug诊断循环、TDD循环、Sentinel安全审查前置、代码任务产出三段式。⛔禁止只遵守部分规则。检查结果以Step标注输出："强制规则遵守：✅ 全部遵守"或"强制规则遵守：⚠️ 未执行X规则，退回补执行"
3. **代码格式规范检查**：确认代码格式符合以下规范——

| 检查项 | 规范 | 判定 |
|--------|------|------|
| 缩进 | Python 4空格/JS 2空格，禁止Tab与空格混用 | Tab+空格混用→⚠️退回修正 |
| 编码声明 | Python文件首行`# -*- coding: utf-8 -*-`（仅Python2兼容场景） | 缺失→⚠️补全（Python3默认UTF-8可省略） |
| 文件编码 | 所有文件I/O显式指定`encoding='utf-8'` | 缺失→⚠️补全（防止Windows默认GBK乱码） |
| 函数文档 | 每个函数/方法有docstring（功能+参数+返回值） | 缺失→⚠️补全（私有辅助函数可简化为单行） |
| 类型标注 | Python函数签名含类型标注（参数+返回值） | 缺失→⚠️补全（适配渐进式标注，已有代码可逐批补全） |
| 错误处理 | 异常捕获指定具体异常类型，禁止裸`except:` | 裸except→⚠️修正为具体类型 |
| 资源管理 | 文件/连接使用`with`语句或`try-finally`确保释放 | 未释放→⚠️修正 |
| 命名规范 | 变量/函数snake_case，类PascalCase，常量UPPER_SNAKE | 不一致→⚠️修正 |

4. **文档格式检查（当编码型参与文档生成时）**：编码型在调用`generate_docx.py`前，除Crystallize阶段7项预检查外，额外执行以下代码级文档格式检查——

| 检查项 | 规范 | 判定 |
|--------|------|------|
| content_data结构 | **列表格式**`[{"h1":标题,"sections":[...]}]`，外层必须为list（dict会触发FormatValidationError报错）；每元素含h1(str)+sections(list)，每section含h2(str)+content(str或list)或paragraphs(list)+可选subsections(list)，每subsection含h3(str)+content(str或list)或paragraphs(list) | 结构不合法→⚠️退回修正。⛔禁止用heading/title/name替代h2，禁止用heading/title/name替代h3，⛔禁止将外层写成dict。generate_docx.py会拒绝错误字段名与dict外层。 |
| 标题层级 | H1=chapter的h1，H2=section的h2，H3=subsection的h3，禁止跨级（H1直跳H3）。⛔禁止用heading字段名，必须用h2/h3。 | 跨级或字段名错误→⚠️修正 |
| 编号一致性 | 所有同级标题编号连续（1/2/3...），无跳号/重号 | 不一致→⚠️修正编号 |
| 表格格式 | Markdown表格含表头行+分隔行+数据行，列数一致 | 列数不一致→⚠️修正 |
| 字符编码 | content_data中所有字符串为str类型（非bytes），无混入编码声明 | bytes混入→⚠️decode为str |
| 空值检查 | title/subtitle/h2/h3不得为空字符串或None | 空值→⚠️填写默认值或移除 |
| content_data完整示例 | 见下方"content_data完整示例"——⛔生成docx前必须对照此示例核对字段名 | 字段名不匹配→⚠️退回修正 |

**content_data完整示例（⛔生成docx前必须核对，字段名必须与此示例完全一致）**：

```python
content_data = [
    {
        "h1": "第一章 本地教育信息化市场概况",
        "sections": [
            {
                "h2": "1.1 市场规模与增长趋势",
                "content": "某市2024年数字经济核心产业增加值560.62亿元。",  # content可为字符串(按换行拆多段)或列表
                # "paragraphs": ["段落1", "段落2"],  # 也可用paragraphs替代content(列表)
                "subsections": [
                    {
                        "h3": "1.1.1 细分市场分析",
                        "content": "教育信息化投入持续增长。",
                        # "paragraphs": ["段落1"],  # subsection同样支持两种字段
                    }
                ],
                "tables": [  # 可选，表格列表
                    {"headers": ["指标", "数值"], "rows": [["增长率", "7.1%"]]}
                ]
            }
        ]
    }
]
```

⛔**字段名禁令**：generate_docx.py第1416行有验证逻辑会拒绝`title`/`heading`/`section`/`name`/`subtitle`作为h2替代字段名，必须使用`h2`作为节标题字段名，`h3`作为子节标题字段名。段落内容用`content`(字符串或列表)或`paragraphs`(列表)均可，但`title`/`heading`/`section`/`name`不可用。

5. **检查结果汇总**：以上4项检查全部通过后，编码型输出汇总Step标注："代码格式与步骤检查：✅ 步骤完整性+强制规则+格式规范+文档格式全部通过"。任一未通过→标注失败项+退回修正+重新检查，⛔禁止带着检查错误提交代码变更

- 所有运维操作须经[Sentinel]安全审查前置

- **深度检测授权**：内存特征检索、原始证据导出、在线信誉查询等深度动作须经用户明确授权后方可执行，且须说明性能/隐私影响
