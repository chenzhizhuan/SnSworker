# TeleAgent 每日积分自动领取

## 概述

通过 PowerShell 脚本模拟鼠标操作，自动完成 TeleAgent 桌面客户端的每日积分领取。脚本首先启动 TeleAgent 进程确保客户端就绪，然后动态定位窗口位置，通过像素扫描精确定位蓝色「立即领取」按钮，点击后验证领取结果，全程无需人工干预。

**v3.9 优化**：新增自动恢复机制——检测到渲染进程崩溃/白屏等故障时，原地重试失败后自动杀掉所有 TeleAgent 进程并重启客户端再重试。新增 `Restart-Client` 函数实现进程清理→重启→等待窗口就绪的完整恢复流程。

**v3.8 优化**：冷启动场景修复——窗口就绪判定从 >100x100 改为 >800x600，排除加载/登录小窗口；冷启动后额外等待10秒确保主界面完全加载。

## 触发场景

- 用户提到"领取积分"、"每日积分"、"积分打卡"、"签到积分"等关键词
- 定时任务每天 09:00 自动调用
- 用户主动要求"帮我领取积分"、"今天积分领了吗"

## 积分规则

| 类型 | 积分 | 有效期 |
|------|------|--------|
| 每日打卡 | +100 | 当日有效 |
| 每月登录 | +3000 | 当月有效 |
| 首次登录 | +3000 | 永久 |

每日积分需在客户端内点击领取，无网页端 API 可调用。

## 执行流程

> **重要**：脚本操作 TeleAgent 窗口会与当前对话产生冲突，直接在对话中执行可能被"已暂停本轮思考与执行"中断。应通过守护进程 `run` 命令提交到**独立会话**执行，详见下方"窗口冲突与独立会话执行"章节。

1. 运行脚本：

```bash
powershell -ExecutionPolicy Bypass -File scripts/claim_points.ps1
```

2. 脚本自动完成以下步骤（v3.9）：
    - **Step 0**：清理旧临时截图文件（保留最近1天）
    - **Step 1**：检测 TeleAgent 进程（v3.5 区分主/子进程），主进程已在运行则跳过，未运行/仅有残留子进程则清理后启动客户端，再轮询查找窗口句柄（最长 60 秒）；v3.8：窗口就绪判定从 >100x100 改为 >800x600，排除冷启动时的加载/登录小窗口（436x438）；冷启动后额外等待10秒确保主界面完全加载；窗口就绪后检查可见性（最小化自动恢复、记录 IsWindowVisible 状态）；窗口不可见时调用 Retry-InPlace 原地重试
    - **Step 2**：前置窗口到前台
    - **Step 3**：截图初始界面（BitBlt 优先，PrintWindow 备选）；截图后白屏检测（深色像素检测法，20x20网格采样400点，深色像素<3判白屏），白屏则重新聚焦窗口等待5秒后重试截图（最多3次），3次仍白屏才调用 Retry-InPlace 原地重试
    - **Step 4**：点击左下角头像打开个人菜单（6.6%宽 96%高，含像素差异验证，3次重试+位置微调）
    - **Step 5**：像素扫描蓝色「立即领取」按钮；未找到按钮时先白屏检测，白屏则原地重试而非推断"已领"
    - 若未找到蓝色按钮，正向检测紫色「今日已领」按钮
    - **Step 6**：点击前先截图记录累计积分区域像素（作为验证基准）
    - **Step 6b**：点击蓝色「立即领取」按钮
    - **Step 7**：三重验证——累计积分区域像素变化（主要）+ 蓝色按钮消失 + 紫色按钮出现
    - **Step 8**：验证未通过时调用 Retry-InPlace 两级重试（v3.9）：第1级原地重试（重新聚焦窗口→等待10秒→以子进程重新执行脚本，不杀进程）；第1级失败后第2级自动重启客户端（`Restart-Client`：杀所有进程→等3秒→重启客户端→等窗口就绪→冷启动等待10秒）再重新执行脚本
    - 关闭菜单
3. 脚本输出 JSON 格式结果（以 `RESULT:` 前缀标记）

## 退出码说明

| 退出码 | 状态 | 说明 |
|--------|------|------|
| 0 | success | 领取成功 |
| 1 | already_claimed | 今日已领取，无需重复操作 |
| 2 | client_not_running | 客户端未运行且自动启动失败 |
| 3 | window_not_found | 窗口定位失败 |
| 4 | button_not_found | 未找到按钮，界面可能已变化 |
| 5 | claim_unverified | 点击后未确认成功，需手动检查 |

## 技术细节

### 关键技术选型（为什么不用其他方案）

**为什么不用 UI Automation（UIA）？**
TeleAgent 是 Electron 应用，其 UI Automation 树仅暴露 Pane 节点，无法枚举按钮、菜单等交互元素。因此无法通过 UIA 定位「立即领取」按钮，只能采用像素扫描方案。

**为什么不用 `mouse_event` 而用 `SendInput`？**
Electron 应用对 `mouse_event` API 的模拟点击无响应（点击事件不触发）。必须使用 `SendInput` API 发送底层输入事件，Electron 才能正确接收并处理点击。这是本脚本选择 `SendInput` 的根本原因。

**为什么用 BitBlt 优先 + PrintWindow 备选？（v3.0 变更）**
- `PrintWindow` 对 Electron 窗口经常返回黑屏（尤其在窗口刚启动或 GPU 渲染未完成时），是 v2.x 的主要故障源
- v3.0 新增 `BitBlt` 从屏幕 DC 截图作为首选方案：`GetDC(IntPtr.Zero)` 获取屏幕 DC，`BitBlt(SRCCOPY)` 复制窗口区域，不依赖窗口自身 DC 权限
- `PrintWindow` 保留为备选：当 BitBlt 也失败时自动切换
- 截图后检测黑屏（采样100个像素点，>=95个全黑判定为黑屏），黑屏时自动重试 3 次
- 实测 BitBlt 在 TeleAgent 子进程中可正常工作，解决了 v2.x 的黑屏问题

**为什么不用客户端 API？**
TeleAgent 客户端本地服务端口（4397 需 401 认证、19876 返回 404）未暴露可用的积分领取接口，积分领取只能通过客户端 UI 操作完成。

### 自动恢复与两级重试（v3.9 新增）

**问题背景**：客户端渲染进程崩溃后（`Renderer process gone { reason: 'crashed' }`），Electron 主进程不会自动重建渲染进程，窗口变为白屏，v3.7 的原地重试（仅重新聚焦窗口）无法恢复。必须完整重启客户端才能重建渲染进程。

**v3.9 解决方案**：
1. **新增 `Restart-Client` 函数**：
   - 杀掉所有 TeleAgent 进程（主进程 + GPU + 渲染 + 网络 + 守护等全部子进程）
   - 等待 3 秒确保进程退出干净
   - 如有残留进程再次强杀
   - 重新启动 `TeleAgent.exe`
   - 等待 5 秒后轮询查找窗口（>800x600，最长 60 秒，与主流程 Step 1 一致）
   - 冷启动后等待 10 秒确保 UI 完全加载
   - 返回成功/失败
2. **Retry-InPlace 改为两级重试**：
   - **第1级（原地重试）**：不杀进程，关闭菜单→重新聚焦窗口→等待10秒→以子进程重新执行脚本。适用于临时性白屏（UI 渲染延迟、窗口焦点丢失等场景）
   - **第1级失败后**：进入第2级
   - **第2级（自动重启）**：调用 `Restart-Client` 杀所有进程并重启客户端→等待窗口就绪和 UI 加载→以子进程重新执行脚本（RetryCount=0 走完整正常流程）。适用于渲染进程崩溃、GPU 进程异常等需要完整重启的场景
3. **触发场景**：窗口不可见（IsWindowVisible=False）、白屏检测（3次截图均为白屏）、Step 7 验证未通过
4. **安全措施**：两级重试均失败后返回 code=5（claim_unverified），不会无限循环

**为什么不直接重启而是先原地重试？**
重启客户端会中断当前对话会话（杀进程会断开 WebSocket 连接）。原地重试可以在不中断对话的情况下解决临时性问题（如 UI 渲染延迟）。只有在原地重试确认无效后，才执行重启——此时渲染进程已崩溃，对话本来也无法继续，重启是合理的。

### 白屏检测与原地重试（v3.6 新增，v3.7 改进，v3.9 增强自动重启）

**问题背景**：客户端自动更新后或启动后界面可能处于白屏加载状态，UI 模块完全未渲染。此时截图截到纯白界面，像素扫描既找不到蓝色按钮也找不到紫色按钮，旧版本会兜底推断"今日已领"（code=1），导致误判。

**v3.6 解决方案**（白屏检测+重启重试）：
1. **白屏检测函数 IsWhiteScreen**：采样截图100个像素点，白色像素（RGB均>235）>=90个则判定为白屏
2. **窗口不可见检测**：`IsWindowVisible=False` 时不再继续执行，直接触发重试
3. **三个检测点**：
   - Step 1 窗口可见性检查后：不可见 → 重试
   - Step 3 初始截图后：白屏 → 重试
   - Step 5 未找到按钮时：先白屏检测，白屏 → 重试

**v3.7 改进**（原地重试 + 白屏重试循环 + 深色像素检测法）：
- v3.6 的 `Restart-AndRetry` 会杀掉所有 TeleAgent 进程并重启客户端，但客户端正在运行时（如定时任务触发、用户正在对话中），杀进程会中断当前对话会话
- v3.7 改为 `Retry-InPlace`：**不杀进程、不重启客户端**，仅关闭菜单 → 重新聚焦窗口 → 等待10秒 → 以子进程重新执行脚本（最多1次）
- Step 3 新增白屏重试循环：窗口置前后 UI 可能需要数秒才能渲染完成，单次截图白屏不代表 UI 不可恢复。改为最多3次截图重试（每次间隔5秒并重新聚焦窗口），3次仍白屏才触发 Retry-InPlace
- **IsWhiteScreen 改为深色像素检测法**：TeleAgent UI 使用浅色主题（背景 R248 G249 B250），白色像素占比高达92%，v3.6 的白色占比检测（>=90%判定白屏）会误判正常 UI 为白屏。v3.7 改为 20x20 网格采样400点，检测是否存在深色像素（RGB任一通道<200），正常 UI 有 10+ 深色像素（文字、图标等），纯白屏为 0，阈值为 <3 判定白屏

**v3.9 新增自动重启**：
- v3.7 的原地重试仅重新聚焦窗口，无法解决渲染进程崩溃导致的白屏
- v3.9 在原地重试失败后新增第2级自动重启：调用 `Restart-Client` 杀所有进程→重启客户端→等待窗口就绪→重新执行脚本
- 详见上方"自动恢复与两级重试"章节

### 进程检测与启动（v3.5 变更）

**v3.5 核心变更：区分主进程与子进程**

Electron 应用会生成多个同名进程（主进程、GPU、渲染、网络服务等），`Get-Process -Name "TeleAgent"` 会匹配所有进程，`Select-Object -First 1` 可能取到子进程导致误判（此前出现过 PID 取到渲染进程的情况）。

**v3.5 主进程判定标准**：
1. 优先：有 `MainWindowHandle` 的进程（持有窗口的即主进程）
2. 备选：命令行不含 `--type=` 参数的进程（Electron 子进程命令行必带 `--type=gpu-process/renderer/utility` 等）

**v3.5 流程**：
1. 获取所有 TeleAgent 进程，判定是否存在主进程
2. 有主进程 → 直接跳过启动，进入窗口查找
3. 仅有子进程无主进程 → 判定客户端未正常运行，清理残留进程后重新启动
4. 完全无进程 → `Start-Process` 启动 `D:\Program Files\TeleAgent\TeleAgent.exe`，等待 5 秒（v3.8 从3秒增至5秒）
5. 轮询查找窗口（每 2 秒，最长 60 秒）：
   - 优先 `FindWindow(null, "TeleAgent")`
   - 兜底 `Get-Process -Name "TeleAgent" | Where { $_.MainWindowHandle -ne 0 }`
   - v3.8：窗口尺寸 >800x600 视为就绪（原 >100x100），排除冷启动时的加载/登录小窗口（436x438）
6. 窗口就绪后检查可见性：
   - 最小化（IsIconic）→ 自动 `ShowWindow(SW_RESTORE)` 恢复
   - 记录可见性状态日志（IsWindowVisible）
7. v3.8：冷启动后额外等待10秒确保主界面完全加载（非冷启动等待3秒）

**v3.2 历史（保留说明）**：检测到主进程就跳过、未检测到才启动，避免中断对话；窗口就绪后再执行截图和点击操作

### 截图方式（v3.0 双方案）

| 方案 | API | 原理 | 优先级 |
|------|-----|------|--------|
| BitBlt | `GetDC(IntPtr.Zero)` + `BitBlt(SRCCOPY)` | 从屏幕 DC 复制窗口区域像素 | 首选 |
| PrintWindow | `PrintWindow(hWnd, hdc, PW_RENDERFULLCONTENT)` | 让窗口自行渲染到提供的 DC | 备选 |

- 两种方案均含黑屏检测（采样100像素，>=95全黑判定黑屏）
- 首选 BitBlt 失败后自动切换 PrintWindow
- 两种均失败则重新前置窗口并重试，最多 3 轮

### 菜单打开验证
- 点击头像前后分别截图，比较左侧区域（0-30%宽，50%-底部）的像素差异
- 差异 > 100 个采样点 -> 菜单已打开
- 差异 <= 100 -> 重试，第2次微调位置至 (7.5%, 94%)，第3次 (5.8%, 97%)
- 每次重试前重新获取窗口位置，防止窗口移动导致坐标偏移

### 按钮定位
- **蓝色「立即领取」按钮**：`B > 140, B > R+50, B > G+30, R < 120, G < 160`，每行蓝色像素 >= 150 且行宽度 >= 180px
- **紫色「今日已领」按钮**：`B > 110, B > G+10, B > R, R > 60` 且非蓝色按钮，每行像素 >= 80 且行宽度 >= 140px
- 扫描范围：窗口左侧 22% 宽度，纵向 63% 到底部（排除上方「去升级」等蓝色元素）
- 若主范围未找到，扩大至 40% 开始扫描
- 找最长的连续宽条行段作为按钮区域，计算中心坐标

### 验证逻辑（v3.3 三重验证）

**v3.3 核心变更：新增累计积分区域像素对比作为主要验证手段**

领取成功后，个人菜单中的累计积分数字会变化（如 2200 -> 2300），导致该区域像素发生变化。以此作为主要验证手段，比单纯依赖按钮颜色变化更可靠。

**累计积分区域定义**：
- 位置：个人菜单中「累计」文字后面的数字区域
- 比例范围：x: 9%-16%（窗口宽），y: 73%-80%（窗口高）
- 基于实际 UI 测量（累计积分数字位于 x:10.8%-13.7%, y:75.4%-78.1%，适当扩大作为扫描区域）

**验证流程**：
1. 点击「立即领取」前先截图记录累计积分区域（Step 6）
2. 点击后重新截图（Step 7）
3. 使用 `CountPixelDiffExact` 逐像素比较点击前后累计积分区域，阈值 >5 个像素差异判定为变化
4. **三重验证判断**：
   - 验证1（主要）：累计积分区域像素变化 -> 领取成功
   - 验证2（次要）：蓝色按钮消失 -> 领取成功
   - 验证3（辅助）：紫色按钮出现 -> 正向确认
5. 累计积分区域变化 OR 蓝色按钮消失，均判定为领取成功
6. 两者均未通过 -> Step 8 原地重试并重新执行整个领取流程
7. 重试仍失败 -> 报告 claim_unverified

**Step 8 重试机制（v3.9 两级重试）**：
- v3.7 将 `Restart-AndRetry` 改为 `Retry-InPlace`，不再杀进程/重启客户端
- v3.9 新增两级重试：第1级原地重试（不杀进程）→ 第2级自动重启客户端（`Restart-Client`）
- 调用场景：窗口不可见、白屏检测、Step 7 验证未通过
- 第1级流程：关闭菜单 → 重新聚焦窗口 → 等10秒 → 以子进程重新执行脚本
- 第1级失败后第2级流程：`Restart-Client`（杀所有进程→重启客户端→等窗口就绪） → 以子进程重新执行脚本（RetryCount=0）
- 两级均失败 -> 报告 claim_unverified
- 子进程的 RESULT 输出会直接传递给父进程

**为什么不用 OCR 读取具体积分数值？**
Windows OCR（`Windows.Media.Ocr`）的异步 API 在 PowerShell 5.1 中需要复杂的 WinRT 互操作调用，兼容性差。改用像素对比方案：不读取具体数值，只比较点击前后该区域的像素是否变化，更简单可靠且无需额外依赖。

**原有的按钮颜色验证仍保留**：
- 蓝色按钮消失 + 紫色按钮出现 -> 领取成功（双重确认）
- 蓝色按钮消失但无紫色按钮 -> 领取成功（单重确认）
- 初始即无蓝色按钮 + 检测到紫色按钮 -> already_claimed（正向确认）
- 初始即无蓝色按钮 + 无紫色按钮 -> already_claimed（推断）

### 坐标计算（v3.0 修正）

### 窗口冲突与独立会话执行（重要）

**问题现象**：脚本通过 `SetForegroundWindow` 将 TeleAgent 窗口置前、截图、点击头像等操作，会与当前对话窗口产生冲突。当在对话中直接执行领取脚本时，窗口操作会打断当前会话的执行流程，导致"已暂停本轮思考与执行"，脚本被中断而无法完成领取。

**根因**：脚本操作 TeleAgent 桌面窗口（置前、截图、模拟点击头像）时，窗口焦点切换会干扰正在进行的对话会话，Electron 应用的窗口状态变化触发客户端内部事件，打断当前会话执行。

**解决方案**：通过定时任务 `run` 命令将领取脚本提交到守护进程队列，在**独立会话**中执行，避开当前对话窗口冲突。

**执行方式**：
```
# 在当前对话中，通过守护进程提交到独立会话执行（而非直接 powershell 调用）
# 守护进程会创建独立会话运行脚本，完成后会话状态变为 idle
```

**验证方式**：因无法直接查看独立会话对话内容，需通过以下方式确认结果：
1. 检查脚本日志输出（`RESULT:` 行的 JSON）
2. 检查临时截图文件
3. 检查客户端日志
